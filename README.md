# groundwork-api

Backend for **Groundwork**, a personal life-system book. NestJS 11, TypeORM 0.3, PostgreSQL (Supabase).

## Setup

```bash
npm install
cp .env.example .env        # already done for you; open .env and set the database password
npm run migration:run       # creates the "groundwork" schema + tables (also runs automatically on start)
npm run dev                 # http://localhost:4000/api
```

**`.env`**

| Variable | What |
|---|---|
| `DATABASE_URL` | Supabase → Project → **Connect** → **Session pooler** (port 5432). The direct `db.<ref>.supabase.co` host is IPv6-only and fails on IPv4 networks with `ENOTFOUND`. URL-encode special characters in the password. Don't add `?sslmode=`. |
| `DB_SSL` | `true` for Supabase. |
| `JWT_SECRET` | Random string, at least 32 chars. Signs the login cookie. |
| `WEB_ORIGIN` | Where the web app runs (CORS). Default `http://localhost:3000`. |
| `COOKIE_SECURE` | `true` when served over HTTPS. |
| `RUN_MIGRATIONS` | `false` to stop the API applying migrations on start. |

## Database: TypeORM entities, generated migrations

The schema is defined **only** in [`src/db/entities.ts`](src/db/entities.ts). Never write migration SQL by hand.

```bash
# 1. change an entity in src/db/entities.ts
# 2. generate a migration from the difference between the entities and the database
npm run migration:generate -- src/migrations/DescribeTheChange
# 3. apply it
npm run migration:run
npm run migration:show      # list applied / pending
npm run migration:revert    # undo the last one
```

Tables live in a dedicated `groundwork` schema, so Supabase's auto-generated REST API (which exposes `public`) can't see them.

## API (all under `/api`, JSON, cookie auth)

| Area | Endpoints |
|---|---|
| Auth | `GET auth/status` · `POST auth/setup` (first run only) · `POST auth/login` · `POST auth/logout` · `POST auth/password` |
| Settings | `GET/PUT settings`: private wave letters, start date, handwriting font · `PUT settings/reading/:book` (`{ last?, marks? }`: where you stopped reading + bookmarks, merged per book) |
| Library (read-only) | `GET library` (volumes with written chapters) · `GET library/:series~:volume` (chapters as Markdown) · `GET library/covers/:slug.svg` |
| Daily page | `GET logs?from&to` · `GET/PUT logs/:date` (partial updates; `notes` = back of the page, HTML) · `GET today?date=` |
| Reviews | `GET/PUT reviews/week/:date` · `GET/PUT reviews/month/:yyyy-mm` · `GET/PUT reviews/year/:yyyy` |
| Book | `GET book/:year`: table of contents (which pages are filled) |
| Roadmaps | `GET/POST maps` · `GET/PATCH/DELETE maps/:id` · `POST maps/:id/nodes` · `PATCH maps/:id/layout` · `POST maps/:id/edges` (409 + loop path on cycles) · `PATCH/DELETE nodes/:id` · `DELETE edges/:id` · `GET next-actions` |
| Other | `GET/PUT/DELETE metrics/:key/:date` · `GET export` · `GET health` |

## Reading books (Markdown library)

Set `LIBRARY_DIR` in `.env` to one or more library roots (comma-separated). Each root needs
`seed/books.json` (the series: `slug`, `title`, `seedDir`, `contentDir`, optional `coverImage` SVG)
and, per series, `<seedDir>/arcs.json` with `volumes: [{ id, number, title, chapterStart, chapterEnd }]`.
Chapters are `<contentDir>/ch-0001.md` … with YAML front matter (`title`, `epigraph`,
`epigraph_attribution`). Every volume with at least one written chapter becomes a book in the universe.

The files stay Markdown and are only ever read: there is no write endpoint, and only files named by
the registry are opened (ids from URLs are looked up, never joined into paths). Restart the API after
changing `LIBRARY_DIR`; new chapters show up on their own.

## Layout

```
src/
  db/          entities.ts (schema) · data-source.ts (TypeORM config, used by app + CLI) · migrate-cli.ts
  migrations/  generated by TypeORM, do not hand-edit
  graph/       pure roadmap engine: cycle check, topo order, locked/available, progress (+ tests)
  library/     read-only Markdown library (+ tests)
  auth/ maps/ logs/ reviews/ metrics/   feature modules
```
